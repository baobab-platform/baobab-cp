# Canonical Contract Matrix — `baobab-platform/shared` ↔ `baobab-platform/baobab-cp`

Companion to `shared-control-plane-audit.md`. One row per canonical concept that
`baobab-platform/shared` defines (via an accepted ADR and/or a `contracts/control-plane/v1/*`
schema) and that `baobab-cp` implements or is expected to implement. "Shared source" cites
the accepted contract; concepts that exist only in the *Proposed* `Baobab Canonical Mapping
Model.md` document are marked as such and are not treated as binding for status purposes.

Legend — **Naming**: Match / Partial / Mismatch. **Test status**: Covered (real Postgres or
meaningful unit test) / Partial (mocked/in-memory only) / None.

## Notes on this matrix

- Rows marked "Mapping Model §N (Proposed, informative)" cite the *aspirational*
  `Baobab Canonical Mapping Model.md` document, whose own header states `Status: Proposed
  Canonical Architecture`. It is used here only to give vocabulary and structure to
  concepts `baobab-cp` has already chosen to build toward (via its own, also-Proposed,
  `ADR-BCP-001`) — it is not being treated as an accepted external obligation the way
  ADR-0001–0005 and the `contracts/control-plane/v1/*.schema.json` files are.
- "DB representation" cites the migration file that actually creates the table, verified by
  reading the `.sql` file directly — not by trusting `ADR-BCP-001`'s prose description of
  what that migration "SHALL" contain, which in several cases (canonical registry, mapping,
  capability, engine topology) describes a materially richer table than what is actually
  migrated. Where the two disagree, this matrix follows the real `.sql` file.
- This matrix should be treated as a living document: re-run this comparison whenever
  `contracts.lock.yaml`'s pinned commit changes, or whenever a new migration is added.

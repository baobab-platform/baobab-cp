## 1. Verdict

The backend has progressed substantially beyond the September frontend audit. The Console itself remains a
**foundation-only implementation**. The root README incorrectly claimed an A4 context-resolution milestone and said
the repository owned no UI; the FE-00 snapshot incorrectly represented later administrative API work as absent.
The correct near-term goal is a secure, end-to-end vertical journey, **not** another round of static dashboard cards.

## 3. Corrected dependency and ownership boundaries

```text
User browser
   │ Secure HttpOnly session (FE-03: not implemented)
   ▼
Next.js CP Console BFF
   │ server-only typed CP client; never browser bearer tokens
   ▼
Go Control Plane API
   │ verifies IAM identity AND evaluates CP administrative authority
   ▼
Canonical organisation / tenant / provisioning / operations state
   │
   └──── Shared governs contracts; IAM governs authentication and federation
```

- FE-03 must use the **current** provider-neutral IAM / federation decisions under ADR-IAM-0033. The September
  statement that all Keycloak work was on hold pending an Ory migration is **historical, not current guidance**.
  Verify the registered confidential client, issuer, redirect URIs, audience and logout support against IAM before
  writing the login flow. Do **not** assume those runtime resources are provisioned.
- The caller's effective authority endpoint can inform navigation **after authentication**; it does not replace
  server-side authorisation of each CP command.
- The Console owns **presentation and browser session/BFF mediation**, never tenant identity, durable governance
  aggregates, provisioning state or evidence verdicts.
- ADR-BCP-026/027 amend the enterprise-onboarding journey toward progressive evidence and organisation-first
  identity. Keep legal actors, admission approval, subscriptions, entitlements, provisioning and activation separate.

**First product-level acceptance journey:** an authenticated applicant submits a real application, a distinct
authorised reviewer/decider evaluates it, an onboarding operator requests admission-to-tenant handoff, a distinct
authoriser approves it, and an operator can trace plan → operation → readiness without ever mistaking `APPROVED`
for `ACTIVE`.

## 5. Remaining questions that cannot be assumed closed

1. Is the **Console-specific confidential IAM client** provisioned in the target environment and verified under
   the permanent federation architecture? Verify rather than treating a workforce/public client as suitable.
2. Which CP administrative route groups and grants are enabled in that environment? Source handlers alone cannot
   answer that; inspect router configuration and authorisation tests.
3. Are organisation and tenant list/search read models sufficient for paginated Console navigation? Check
   OpenAPI, actual list handlers and scope filtering before promising a global catalogue.
4. Are all applicant/evidence/browser upload routes available and lawful for the selected onboarding channel?
   Evidence registration and verified content retrieval are distinct.
5. What staging environment demonstrates E2E IAM → BFF → CP → provisioning → readback, including blocked paths?

## 6. Non-negotiable engineering discipline

Before every gate: inspect current CP `main` and open PRs, current Shared pin and generated client, current IAM
confidential-client configuration, affected ADRs and the CP OpenAPI drift test. Implement one vertical at a time,
with keyboard/accessibility, error/empty/permission tests, no-store semantics and negative authorisation coverage.
Never add a fake durable state model, a browser-side privileged API call or a production showcase with invented data.

This rebaseline does **not** close FE-03 or certify production onboarding.
